## 1. 問題定義

每月的 EIS Review 檔記錄全公司各部門、各員工、各專案的實際人力投入（FTE）。目前的 review 是在 Excel 裡手工做月對月比較（檔內已有 `Project 5 vs.6`、`FU Project Code` 等人工 MoM 分頁）。

本專案自動化並延伸這件事，回答三個問題：

1. **人力配置失衡／碎片化** — 誰被切得太碎、哪個單位配置異常
2. **該撤沒撤／該加沒加** — 專案結案了人沒撤、新專案人上不來
3. **單位之間的橫向比較** — 哪些部門是離群值

**明確不做**：投入產出比。需要專案進度／里程碑，而 `CURRENT_PHASE` 全為「PDPM資料未更新」，硬做會產出不可信的指標。

## 3. 架構（方案 A：Python 批次 → 自足單頁 HTML）

### 3.1 選型理由

核心風險是 **join 的正確性**，不是圖表互動性。方案 A 讓對照表與中間產物成為可稽核的檔案；瀏覽器端解析（方案 B）會把驗證邏輯藏進 JS 且無中間產物，出錯時無法回答「這個數字怎麼來的」——以本專案的髒 join 情境，這是致命傷。DuckDB/notebook（方案 C）不符合「單頁 HTML、可投影」的用法。

使用情境：每月 review 會議投影 ＋ 自己隨時開來鑽。本機執行，資料不外流（含 4,385 筆員工姓名工號），無部署、無權限問題。

### 3.2 目錄結構

```
dashboard_eis/
├── data/raw/                  # 原始檔，唯讀（忽略 ~$ 鎖檔）
├── config/
│   ├── aliases.yaml           # 專案別名對照（核心資產）
│   ├── function_map.yaml      # EIS_FUNCTION 219 種自由填寫值 → 標準職能
│   ├── plan_exclusions.yaml   # plan 小計列排除（分攤單位小計 + 產品別小計）
│   ├── thresholds.yaml        # 指標門檻
│   └── muted.yaml             # 已知原因、暫時靜音（須附理由）
├── src/
│   ├── ingest.py              # xlsx → 正規化 → facts.parquet
│   ├── reconcile.py           # 對照表 + 驗證關卡
│   ├── metrics.py             # 指標 → data.json
│   └── build.py               # data.json → dashboard.html
├── out/
│   ├── facts.parquet
│   ├── recon_report.md        # 每月必看
│   └── dashboard.html
└── Makefile
```

### 3.3 資料模型

單一長表，所有分析都是它的投影：

```
facts: (yyyymm, dept_code, dept_name, emp_id, emp_name,
        project_code, project_name_raw, project_key,
        eis_function, project_bu, dept_org,
        source, unit_role, fte)
```

| 欄位 | 說明 |
|---|---|
| `source` | `detail`（人力明細）或 `fu_alloc`（FU Project Code）。**僅記錄資料出處**，**不可用來推斷組織身分**（見下）。 |
| `unit_role` | `BU RD` / `BU PM` / `FU RD`，對應組織模型與 plan 的三列結構。**`FU RD` = `dept_org != project_bu`（非本 BU 的支援，含其他 BU）**；否則 `PM` in `eis_function` → `BU PM`；其餘 → `BU RD`。此規則完全重現人工樞紐（19/19、誤差 0）。詳見 AGENTS.md。 |
| `project_bu` | 專案歸屬 BU（來自 `人力明細.BU`）。FU 表無此欄，靠 BR code 反查補上——此 join 乾淨可靠。 |
| `dept_org` | 部門所屬組織（來自 `百分比分攤.BU`）。**與 `project_bu` 語意不同，勿混用。** |
| `project_key` | 對照表正規化後的標準名 |
| `project_name_raw` | 原始值，保留以供回溯 |
| `emp_id`/`emp_name` | 僅 `source=detail` 有值；`fu_alloc` 無逐人資料 |

**組裝規則**：

```
facts_fte  = ProjectCode人力（D + Y，全公司）        ← FTE 正式來源，無需去重
             排除 dept_code[0] == 'H'（製造）
facts_人   = 人力明細（僅 D 組）                      ← 碎片化用，含工號
```

`ProjectCode人力` 已含 D 與 Y 兩組且不重疊，**不需要「人力明細 + FU 表去重」那套組裝**（初版做法，源自誤判 `ProjectCode人力` 為衍生資料）。

> ⚠ **`unit_role` 不可用 `source` 或部門首字推斷**，須用 `dept_org != project_bu`。詳見 AGENTS.md。

**月快照不可變性**：以檔案月份為分區主鍵寫入，重跑同月只覆蓋該月。已驗證 05/06 兩檔共有的 1,104 組數值完全一致，無事後修改。

## 4. 對照表與驗證關卡

### 4.1 aliases.yaml

人工維護、進版控。**工具可用字串相似度提示候選，嚴禁自動套用**——猜錯會靜默污染數字。已確認別名見 AGENTS.md。

### 4.2 plan_exclusions.yaml

`人力分攤-PM` 的 `人力分攤單位 = 人力編列 BU RD+PM` 為小計列（= BU RD 178.8 + BU PM 42.1 = 220.8），會被誤讀成名為 `218` 的專案。

排除後 plan 六月真實總量 = **335.5**（FU RD 114.7 + BU RD 178.8 + BU PM 42.0）。

### 4.3 recon_report.md（每月重跑後必看）

1. **未對照專案** — 有 FTE 但對不到 plan，按 FTE 排序。人工判斷是「新別名」或「真的計畫外專案」。
2. **plan/actual 總量健檢** — 需**分「已解釋／未解釋」**，未解釋部分要有具體數字。
   （教訓：初版的 2.5 倍紅燈被歸類成「plan 定義不明」，實際上是漏算 FU + 未排除小計列。**只給一個比值的紅燈會變成背景噪音。**）
3. **月間結構飄移** — 分頁名／欄名變動、列數異常變化。
4. **迴歸測試（兩側都有人工／系統對照答案）**
   - **FU 側**：逐專案 FU FTE 須與 `Project N vs.N+1` 分頁完全吻合（202606 已驗證 19/19、96.19 = 96.19、誤差 0）
   - **BU 側**：`人力明細` 聚合須與 `ProjectCode人力` 的 D 組完全吻合（202606 已驗證 2,890/2,890、1,737.00 = 1,737.00、0 筆不符）
   - **分攤邏輯**：Y 組「分攤合計 ÷ 主管填寫人力」須為 1.00（202606 已驗證 218/218）
   任一項不符即 ingest 壞了。
5. **製造排除量** — 須顯示排除的 `H` 開頭 FTE（202606 為 6,603.91），不可靜默過濾。

### 4.4 失敗要大聲

未對照的專案**不得丟棄**，須彙總為 `unmapped_fte` 常駐顯示於首頁。對照表失效時第一眼就會看到「有 N FTE 未歸屬」，而非看到數字全錯但外觀正常的圖。

紅燈**只警告、不擋建置**（需求方決定 2026-07-15）。

## 5. 指標定義

原則：每個指標都要能回答「所以我該做什麼」。

### 5.1 plan vs actual — 三層分別比對（核心指標）

**必須依組織模型拆成 `FU RD` / `BU RD` / `BU PM` 三層**，不可只看專案總量。

理由（202606 實例）：Foxtrot 總量 72.1 / plan 67 = 108%，看似正常。拆開後：

| | plan | actual | 達成率 |
|---|---:|---:|---:|
| FU RD | 36.0 | 25.7 | **71%** |
| BU RD | 24.0 | 42.3 | **176%** |
| BU PM | 7.0 | 4.2 | 60% |

**真相是「FU 支援不到位，BU 用自己的 RD 硬補」**——總量達標完全掩蓋了這個結構問題。同一模式在 D7K3（FU 59% / BU 131%）、D5K2（FU 48% / BU 123%）一致出現，是**系統性現象而非個案**。

BU10 全體（202606，plan 用 **`人力分攤-updated`**、含 KILO 別名、排除兩類小計列）：

| | plan | actual | 達成率 |
|---|---:|---:|---:|
| **FU RD** | 106.7 | 96.2 | **90%** |
| **BU RD** | 167.0 | 167.9 | **101%** |
| **BU PM** | 38.8 | 35.5 | **92%** |
| **總計** | **312.4** | **299.6** | **96%** |

**三層都在 90~101%，總量健康。「FU 系統性不到位」的結論是錯的**——先前版本（45%→49%→56%→68%）全是分母錯誤的產物：把計畫外專案的 FU 貢獻排除，卻保留 plan 的完整分母。

**FU/BU 失衡是個別大專案的現象，不是系統性問題**：Foxtrot FU 83% / BU RD 159%、D7K3 FU 60% / BU RD 130%、D5K2 FU 46% / BU RD 124%。BU 確實在大專案上超配自補，但總量上 FU 到位 90%。

### 真正的訊號：總量掩蓋結構

| | FTE |
|---|---:|
| 編了計畫但完全沒動 | 46.9 |
| 真正的計畫外（已排除 RFQ 18.5、Mania_S 1.5） | 37.0 |
| 其中「計畫已收、人還在」 | **14.1** |

> ⚠ **上面兩個數字（46.9 / 37.0）不可作為管理發現呈現**（2026-07-15 紅隊）。
> 名字對不上的專案**必然**在兩邊各留一半，兩半**必然接近相抵**——**「幾乎相抵」是失敗 join 的算術簽名，不是洞見**。這兩個數字的大小直接由 `aliases.yaml` 的覆蓋率決定。
> 在 plan 取得 `PROJECTCODE` 欄之前，這兩份清單有相當比例是 join 產物。**唯一穩健的是「計畫已收、人還在」14.1**（那四個專案 plan/actual 兩側都對得上）。

### ⭐ 編制超出（真訊號，取代錯誤的「編制貼滿」）

`人力分攤-updated` **列 131 `不足/超出人力` = 編制 203（列 129 硬編）− plan 編列（列 130）**，PM 已經算好：

| 1月 | 2月 | 3月 | 4月 | 5月 | **6月** | 7月 | 8月 | 9月 | **10月** | 11月 | 12月 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| +10.0 | +11.2 | +8.3 | +7.4 | +8.3 | **−2.8** | −7.9 | −8.9 | −8.7 | **−25.4** | −12.4 | −12.4 |

**BU10 從六月起超編，十月缺 25.4 人。**

> ⚠ **初版的「編制已貼滿 205.8 / 205.7」是錯誤發現**：拿列 130（plan 自己的 BU RD+BU PM 加總）當編制，等於把 205.75 減 205.75。詳見 AGENTS.md 的錯誤紀錄。

### 設計缺口：plan 側沒有驗證

三項迴歸測試（§4.3）**全在 actual 側**，但五次翻轉**全在 plan 側**。plan 側需對等的驗證關卡——已知可用的自我驗證見 AGENTS.md。
**任何從 plan 讀出的數字，都須先確認該列的公式與上下相鄰列**（用 `data_only=False` 讀公式）。

其他值得單獨追的專案：

- **THORPE**：FU RD 300%（1.5→4.5）、BU PM 377%（1.0→3.8）——**與其他專案模式相反，各方都超編**。是 plan 編太少還是投入過度？
- **VASCO**：BU RD **0%**（plan 4 人、BU10 一個 RD 都沒派，只有 1 個 PM），FU 從 6.0 砍到 2.0——**實質停擺，但帳上仍有 3 FTE**，不會被「歸零」判準抓到。

### 5.2 該撤沒撤／該加沒加（專案層級）

**前置**：計算前必須先套 `aliases.yaml`、排除 `H`（製造）、排除 `^(BU10_RFQ|TR_BU10_)`（報價階段，本就不編 plan，202606 共 18.50 FTE）。少任一步，異常清單就是錯的。

| 訊號 | 判準 | 202606 實例 |
|---|---|---|
| **計畫已收、人還在**（最強訊號） | plan **歸零**但 actual > 0 | **D5K 4.85、D7K 4.75、VASCO 3.00、Mania_S 1.50 → 14.1 FTE**。`-updated` 已把四者 plan 歸零（Mania-S 自 4 月起），人力仍掛著。**「該撤沒撤」最純粹的形式** |
| **活躍但未入計畫** | plan 從未編列、actual > 0 且**成長中** | **Q11 9.89**（128 個 FU 部門、5→6 月 +2.87）。**一個吃掉 10 FTE、正在爬升的專案，為何不在計畫裡？** |
| **該加沒加** | **plan 已編列 N 個月、actual 仍為 0**（N 越大越嚴重） | **Vega：N=6**，曲線 5.7→5.7→12.5→17.5→17.5→17.5，編半年還加碼、零人力。<br>對照 ZZTop-II：N=1（本月才首次編列），**actual=0 屬正常，不可標記** |
| **超配** | actual/plan > 110%，連續 ≥2 月 | THORPE 159% |
| **中途撤除** | 某 (部門,專案) 前月有 FTE、本月整列消失 | **VASCO**：5 月 FU 支援 6.0（14 個部門），6 月剩 2.0（僅 AI競爭力中心）——軟體技術中心 13 個部門、4.0 FTE 全數撤出。**注意：VASCO 的 plan 已歸零，故此撤除是計畫內的收尾；異常的是「還留著 3 FTE」而非「撤走了 4 FTE」** |
| **持續短缺** | actual/plan < 70% 且趨勢未收斂 | Selena 41%、VASCO 29%、ZZTOP 17%、SPK1 40% |
| **殭屍專案** | 連續 ≥3 月 `0 < FTE < 1.0` 且無成長 | 待六個月資料 |

**「中途撤除」只能靠逐月比對 M 檔取得**——用次月檔的前月欄會把它整個抹掉（AGENTS.md「取月規則」）。這是本類指標最重要的訊號來源。

門檻（110%／70%／連續月數）進 `thresholds.yaml`，由需求方依實務調整。

### 5.3 碎片化（人的層級）

**只跑 `source=detail`**（D 組 64 部門、255 人）。依據是「有無逐人資料」，非「BU vs FU」——工業設計中心是 FU 但屬 D 組，應納入。

每人每月：

```
focus = Σ(share_i²)     # Herfindahl。1.0 = 全心一個專案；0.5 = 均分兩個
```

預設門檻 `focus < 0.5 且 專案數 ≥ 3`。用 HHI 而非專案數：`0.9/0.1` 與 `0.5/0.5` 都是兩個專案，但前者幾乎無切換成本——**專案數會誤報，HHI 不會**。

### 5.4 單位橫向比較（部門層級）

每部門每月：`總FTE`、`專案數`、`人均專案數`、`平均 focus`（僅 D 組）、`MoM 變化`。

475 個部門**只呈現離群值**（IQR 或 z-score），不列全表。

### 5.5 填報黑洞（N 組）

呈現 N 組（主管填寫人力 = 0）的 112 部門 / 338 HR，但**須分類**：

- **行政/後勤/IT 單位**（採購資材中心 29、台灣服務管理中心 20 等）→ 填 0 合理，摺疊顯示
- **31 個 BU10 部門** → 需求方待判斷，展開顯示

**不可逕自標記為異常**（AGENTS.md）。

## 6. UI 設計

單頁、由上而下、倒金字塔：

1. **本月焦點** — 自動產生的「值得討論的 N 件事」，按 `影響FTE × 嚴重度` 排序取 top 8。可用 `muted.yaml` 靜音已知項目。**這一區就是會議議程。**
2. **資料健康度** — 窄 banner，常駐不可摺疊：`unmapped_fte`、plan/actual 未解釋差額、`缺 EIS_FUNCTION: 39%`
3. **BU10 plan vs actual**（內層）— **三層（FU RD / BU RD / BU PM）對照表** + 六個月 sparkline
4. **全公司結構**（外層）— 離群部門 + 碎片化 top N，可下鑽到人（僅 D 組）

### 6.1 視覺方向

**編輯式（editorial）**：serif 標題數字、大量留白、accent bar 標記嚴重度。此物一個月看一次、要投影、要讀，本質接近**報告**而非監控台。明確避開「sidebar + cards + charts 無觀點」的樣板。

色頭卡若使用，須為「單一圓角底卡 + 只圓上緣的標頭 band」，完成後放大交界處目視確認無凹口。

### 6.2 明確不做（YAGNI）

即時查詢、全表瀏覽、自訂篩選器。用法是「每月一次、投影 + 自己鑽」，這些是 dashboard 的反射動作但非需求。
